# meshcore-http-gateway 🌉📡

**Ваша MeshCore-станция, но с HTTP API.**

meshcore-http-gateway — **тонкий HTTP-шлюз** к LoRa-устройству
[MeshCore](https://meshcore.io): всё, что принимает радио, отдаётся через
`GET /get`, а всё, что вы отправляете на `POST /send`, уходит в эфир. Никаких
команд бота, никакого Telegram, никаких плагинов — просто мост между
HTTP-клиентами и радио.

Это тот слой, который нужен, когда *другой* программе надо работать в mesh-сети:
LLM-агент, скрипт домашней автоматизации, собственный дашборд, демон
уведомлений — всё, что умеет HTTP, теперь умеет и LoRa.

## Зачем это нужно

- 🔌 **Двусторонний API.** Опрашивайте `/get` (или курсорный `/messages`) за
  новыми сообщениями, отправляйте на `/send`, смотрите справочники `/contacts`
  и `/channels`. Без SDK, без websocket, без церемоний.
- 📥 **Ничего не теряется.** Сообщения, пришедшие пока сервер был выключен,
  синхронизируются из памяти устройства при старте и отдаются как непрочитанные.
- 📤 **Честные отправки.** `/send` ждёт, пока устройство не подтвердит, что
  сообщение реально ушло, — и сообщает, какая именно произошла ошибка, с
  правильным HTTP-кодом.
- 🔐 **Опциональная авторизация по bearer-токену.** Один ключ в конфиге;
  оставьте пустым — и локально всё работает без лишних телодвижений.
- 🛰️ **Рассчитано на плохое радио.** Та же механика отправки, что и у полного
  бота: ретраи с паузами, работа с сохранённым/флудовым путём, многократная
  передача канальных сообщений с адаптивной ранней остановкой.
- 💤 **Самовосстанавливающееся соединение.** Периодическая статистика держит
  BLE-связь «тёплой» и запускает автоматический реконнект при отвале устройства.

## Запуск

```sh
go run .
# или соберите:
go build -o meshcore-http-gateway . && ./meshcore-http-gateway
```

Бинарник читает `config.yaml` из рабочей директории — секции `Server` и
`Connection`, описанные ниже. Это подмножество общего семейного формата, так
что комбинированный `config.yaml`, общий с ботом или голосовым мостом,
работает здесь без изменений.

### Конфигурация

Все опции живут в секции `Server` файла `config.yaml`:

```yaml
Server:
  listen: ":8080"        # адрес, на котором слушать (по умолчанию :8080)
  token: "s3cret"        # опционально; пусто = без авторизации

Connection:
  type: "bt"             # "bt" (BLE, по умолчанию) или "serial"
  serial_port: "/dev/ttyUSB0"
  serial_baud: 115200
  channel_transmissions: 3   # максимум передач одного канального сообщения (по умолчанию 3)
```

| Ключ | По умолчанию | Значение |
|---|---|---|
| `Server.listen` | `:8080` | `host:port` HTTP-сервера |
| `Server.token` | *(пусто)* | Если задан, каждый запрос должен содержать `Authorization: Bearer <token>` |
| `Connection.*` | как у бота | Транспорт до устройства — BLE-скан или USB-serial |

## API

### `GET /get` — прочитать новые (непрочитанные) сообщения

Возвращает всё, что пришло с момента **последнего успешного `/get`** — чтение
помечает сообщения прочитанными и очищает очередь. Опрашивайте как угодно часто;
пустой инбокс возвращает `{"messages":[]}`, а не ошибку.

```sh
curl -H "Authorization: Bearer s3cret" localhost:8080/get
```

```json
{
  "messages": [
    {
      "id": 42,
      "type": "dm",
      "sender": "Короед",
      "sender_key": "a1b2c3d4e5f6…",
      "channel": "",
      "channel_index": -1,
      "text": "ping, кто тут?",
      "timestamp": "2026-10-25T12:00:00Z",
      "received_at": "2026-10-25T12:00:03Z"
    },
    {
      "id": 43,
      "type": "channel",
      "sender": "Wire",
      "sender_key": "",
      "channel": "public",
      "channel_index": 0,
      "text": "погода портится",
      "timestamp": "2026-10-25T12:00:10Z",
      "received_at": "2026-10-25T12:00:11Z"
    }
  ]
}
```

**Поля**

| Поле | `type: "dm"` | `type: "channel"` |
|---|---|---|
| `sender` | имя контакта или `?<6-hex>`, если ключ неизвестен | имя, которым отправитель подписал сообщение |
| `sender_key` | полный hex публичный ключ отправителя | `""` |
| `channel` / `channel_index` | `""` / `-1` | имя канала / индекс |
| `timestamp` | mesh-время отправителя | mesh-время отправителя |
| `received_at` | когда *этот сервер* его получил | когда *этот сервер* его получил |
| `id` | последовательный ID, назначается сервером — используйте для дедупликации при переподключениях | то же |

Личные и канальные сообщения приходят в одну очередь, вперемешку, в порядке
поступления.

### `GET /messages?after=<id>` — курсорное чтение (неконкурное)

Семантика `/get` — «прочитал, значит забрал»: все потребители делят один ящик.
Когда сервер опрашивают несколько клиентов, используйте курсорный вариант:
он возвращает всё, что новее `after`, **ничего не удаляя**.

```sh
curl -H "Authorization: Bearer s3cret" "localhost:8080/messages?after=42"
```

```json
{"messages": [ …тот же формат, что у /get… ], "last_id": 57}
```

Запомните наибольший обработанный `id` (или вернувшийся `last_id`) и передайте
его следующим запросом как `after`. `last_id` всегда безопасен как курсор.

### `GET /contacts` / `GET /channels` — справочники

Списки только для чтения — чтобы найти адресата перед `POST /send`:

```json
{"contacts": [{"name": "Короед", "key": "a1b2c3…", "last_seen": "2026-10-25T12:00:00Z"}]}
{"channels": [{"index": 0, "name": "public"}]}
```

`/contacts` отсортирован по имени; `/channels` — по индексу, пустые слоты
пропускаются.

### `POST /send` — отправить сообщение в mesh

```sh
curl -X POST localhost:8080/send \
  -H "Authorization: Bearer s3cret" \
  -H "Content-Type: application/json" \
  -d '{"type": "dm", "to": "Короед", "text": "принято"}'
```

Тело запроса:

| Поле | Обязательно | Значение |
|---|---|---|
| `type` | ✔ | `"dm"` или `"channel"` |
| `to` | ✔ | DM: **имя** контакта или hex-**префикс публичного ключа**. Канал: **имя** канала или числовой **индекс** |
| `text` | ✔ | текст сообщения (непустой) |
| `ack` | — | `true` = ждать подтверждения *доставки* (end-to-end, дольше); по умолчанию `false` = подтверждение *отправки* |

Ответы:

| Код | Тело | Когда |
|---|---|---|
| `200` | `{"status":"sent"}` | передано и подтверждено |
| `400` | `{"error":"…"}` | невалидный JSON, отсутствуют `to`/`text`, неверный `type` |
| `401` | `{"error":"…"}` | нет/неверный bearer-токен (только если задан `Server.token`) |
| `404` | `{"error":"contact not found: …"}` / `{"error":"channel not found: …"}` | адресат не найден |
| `502` | `{"error":"…"}` | устройство отклонило отправку или сбой транспорта |
| `504` | `{"error":"…"}` | все попытки истекли без подтверждения |

```json
{"status": "sent"}
```

## Поведение, о котором стоит знать

### `/send` блокирует — и это сделано специально

LoRa медленный. Отправка с ретраями (подтверждения устройства, паузы между
передачами, сбросы пути) честно занимает **10–30 секунд**; `"ack": true` может
занять дольше. HTTP-запрос всё это время остаётся открытым, чтобы ответ отражал
реальный результат.

- Выставьте таймаут HTTP-клиента **от 90 секунд**.
- Параллельные `/send` не конфликтуют: путь к устройству сериализует их, и
  каждый запрос ждёт своей очереди.
- `504` означает *возможно отправлено, без подтверждения* — устройство ещё
  может доставить сообщение с опозданием. Повтор может продублировать его;
  предпочитайте идемпотентные тексты или подождите.

### Семантика непрочитанного

- Для `/get` непрочитанное = **получено с момента вашего последнего `/get`**.
  Нет состояния на клиента: очередь забирает первый же позвонивший.
  Используйте один процесс-поллер или смиритесь с тем, что поллеры делят общий
  ящик.
- Для нескольких читателей есть курсорный эндпоинт: `GET /messages?after=<id>`
  ничего не удаляет, поэтому каждый потребитель ведёт свой курсор.
- Инбокс живёт в памяти и ограничен **1000 сообщений**; при переполнении
  первыми отбрасываются самые старые. Если никто долго не опрашивает, ранние
  сообщения теряются.
- При рестарте синхронизация с устройством восстанавливает в очередь
  непрочитанных сообщения, **сохранённые на устройстве** — это retention самого
  mesh, а не сервера.

### Запуск

Подключение к устройству (BLE-скан или serial) и синхронизация сохранённых
сообщений выполняются **до** старта HTTP-сервера. Если устройство недоступно,
процесс завершается — обслуживать нечего. Дальше сервер живёт всё время работы
процесса; обрывы BLE восстанавливаются в фоне (сообщения, принятые в момент
отвала, просто не видны — это радио).

## Пример: минимальный цикл «опрос-ответ»

```sh
#!/bin/sh
while true; do
  # читаем всё новое, отвечаем на каждое сообщение заготовкой
  resp=$(curl -sf -H "Authorization: Bearer s3cret" localhost:8080/get)
  echo "$resp" | jq -c '.messages[] | select(.type=="dm") | {type, to: .sender, text: ("echo: " + .text)}' |
  while IFS= read -r body; do
    curl -s -X POST localhost:8080/send \
      -H "Authorization: Bearer s3cret" \
      -H "Content-Type: application/json" \
      -d "$body" > /dev/null
  done
  sleep 5
done
```

(Клиенты на Python/Go работают так же: опрашивать `/get`, отправлять на `/send`.)

## Как это соотносится с остальным семейством

| | [meshbot](https://github.com/stempit/meshbot) | этот шлюз | [meshcore-mcp-gateway](https://github.com/stempit/meshcore-mcp-gateway) |
|---|---|---|---|
| Назначение | автономный чат-бот в mesh-сети | HTTP-шлюз для *вашего* кода | мост к голосовому ассистенту XiaoZhi |
| Обработка команд (`.ping`, игры, LLM…) | ✔ | ✘ | ✘ |
| Мосты Telegram / MQTT / алерты | ✔ | ✘ | ✘ |
| Входящие | конвейер dispatcher'а | JSON из `GET /get` | голосовое чтение (`mesh_get_new_messages`) |
| Отправки | ответы, темп задаёт dispatcher | `POST /send`, тот же радио-темп | `mesh_send_message`, тот же радио-темп |
| Соединение с устройством | своё | своё | своё |
| Конфиг | `config.yaml` | `Connection` + `Server` | `Connection` + `MCP` |

Каждое приложение открывает **своё** соединение с устройством — это
независимые фичи. Не направляйте две из них на **одно физическое устройство**
одновременно: MeshCore-компаньон обслуживает одно BLE/serial-соединение.

Карта кода: `main.go` (корень композиции + конфиг), `server.go` (хендлеры,
авторизация, маппинг ошибок). Рантайм устройства (подключение, стартовая
синхронизация, инбокс, keepalive) — из
[meshcore-kit](https://github.com/stempit/meshcore-kit); драйвер
протокола — [meshcore-go](https://github.com/stempit/meshcore-go).
